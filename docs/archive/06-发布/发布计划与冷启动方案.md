# 06 · 发布计划与冷启动方案

> UAE Match ｜ 版本 v1.0.0 ｜ 更新 2026-07-04

---

## 1. 发布目标与前提

**目标**：以最低风险将 UAE Match 推向真实用户，先验证"支付/合规/性能真实表现"，再逐步放量至面向 UAE 华人社群公开发布（对应里程碑 M4）。

**发布前提（硬门槛）**：以下未达成不得进入公开发布——

- 至少一条真实支付链路端到端可用（含回调验签、幂等）。
- 会员权益由服务端订阅状态授权，无前端硬编码 VIP 开关。
- 关键事件通知可触达（站内至少可用）。
- 前端演示态（自动过审/mock）已清除。
- 安全基线达标（强随机密钥走环境变量、生产强制 HTTPS）。
- PDPL 合规审查通过，隐私政策/用户协议上线，数据导出/注销可用。
- 生产使用 PostgreSQL + pgvector，具备基础监控与告警。

## 2. 发布策略：内测 → 灰度 → 公开

采用**三阶段渐进放量**，每阶段设明确准入/退出标准，任一阶段出现 P0 事故即暂停放量或回滚。

| 阶段 | 目标人群 | 规模 | 主要目的 | 准入标准 | 退出/晋级标准 |
|---|---|---|---|---|---|
| **内测（Alpha）** | 核心团队 + 亲友 + 强信任种子 | 20–50 人 | 验证核心链路可用、抓致命 Bug | 功能骨架转真实态、生产环境就绪 | 全链路可用，无 P0/P1 阻塞；一次真实付款成功 |
| **灰度（Beta）** | 邀请制种子用户（UAE 华人社群） | 分批 100 → 300 → 800 | 验证支付/合规/性能真实表现、初步留存与转化 | 内测退出标准达成，监控与值班就绪 | 灰度期无 P0 支付/安全/合规事故；核心指标可持续监测 |
| **公开（GA）** | 面向 UAE 华人社群公开 | 不设硬上限，按承载能力放量 | 规模化获客与运营 | 灰度退出标准达成，合规结论明确 | 进入常态运营迭代 |

### 2.1 灰度范围与放量节奏

- **放量维度**：以**邀请码 + 白名单**控制进入人数，按批次逐步扩大；优先放量渠道来源清晰、真实性高的用户。
- **节奏建议**（每批观察 3–7 天，指标健康再放下一批）：

| 批次 | 累计用户 | 观察重点 |
|---|---|---|
| 灰度批次 1 | ~100 | 注册转化、支付成功率、崩溃率、AI 成本/预算率 |
| 灰度批次 2 | ~300 | 次日留存、匹配成功率、消息回复率 |
| 灰度批次 3 | ~800 | 付费转化率、性能（响应/向量检索）、内容安全事件 |

- **放量闸门**：每批放量前检查上一批"回滚触发条件"（见第 6 节）均未触发，AI 月度预算使用率处于可控区间（预算上限 $500/月）。

## 3. 种子用户获取与冷启动方案

### 3.1 相亲平台的双边冷启动难题

婚恋平台是典型**双边市场**：男性用户需要看到足够女性用户（反之亦然），任何一侧供给不足都会导致体验崩塌、用户流失，形成"没人用→更没人用"的死循环。**冷启动的核心不是拉总量，而是保证"单个地理/圈层内、双边达到可用密度"。**

### 3.2 冷启动策略

| 策略 | 说明 | 适用阶段 |
|---|---|---|
| **单侧聚集 + 单城市聚焦** | 先集中在**迪拜**一个城市做透，避免用户分散到多城导致每城密度不足；可先侧重聚集相对稀缺一侧（如女性用户），用运营手段（邀请激励、优先审核、专属关怀）拉动 | 内测/灰度 |
| **邀请制 / 名额稀缺** | 邀请码进入，制造稀缺感与信任背书；邀请人与被邀人双向奖励（会员时长/增值服务），提升自然获客与真实性 | 全程 |
| **AI 红娘补位体验空窗** | 冷启动早期匹配对象少，"小缘"承担陪伴、引导、日常咨询，降低"没人可聊"的空窗感，延长早期用户存活时间 | 内测/灰度 |
| **线下社群 / 地推** | UAE 华人线下场景（华人社团、商会、留学生/工作圈聚会、教会/同乡会）定点邀请高质量种子用户 | 灰度 |
| **UAE 华人线上社群渠道** | 迪拜/阿布扎比华人微信群、小红书 UAE 华人内容、本地公众号/华人媒体、华人生活服务平台合作导流 | 灰度/公开 |
| **高质量种子人设** | 早期人工把关种子用户质量（真实、认真婚恋意向），奠定"严肃婚恋、非约会"的社区调性 | 内测/灰度 |

### 3.3 冷启动可用密度目标（建议）

- 单城市（迪拜）双边各达到**可用密度**再放量（例如每一侧有足够活跃用户，使新用户注册后能立即获得 ≥3 条有效推荐）。
- 早期以**匹配成功率、消息回复率**作为"密度是否足够"的体感指标，不足则暂缓拉新、优先补稀缺侧。

## 4. 发布检查（呼应上线检查清单）

发布前逐项核对（详见上线检查清单，此处为发布视角摘要）：

- [ ] **功能**：支付/会员授权/通知/照片/编辑资料全部真实态可用。
- [ ] **安全**：无默认/明文密钥入生产；密钥已轮换并走环境变量；生产强制 HTTPS；限流与审计日志开启。
- [ ] **数据**：生产为 PostgreSQL + pgvector；Alembic 可管理迁移；数据备份策略就位。
- [ ] **合规**：PDPL 审查通过；隐私政策/用户协议已上线；数据导出/注销可用；跨境数据处理已披露。
- [ ] **可观测**：错误追踪、核心指标监控、告警通道就绪。
- [ ] **成本**：AI 全局预算（$500/月）与配额生效，用量告警配置。
- [ ] **回滚**：回滚方案与数据回滚点确认可用。
- [ ] **运营**：客服/风控/审核值守与应急预案就位。

## 5. 发布日值班与应急响应

### 5.1 值班安排

| 角色 | 职责 | 覆盖时段 |
|---|---|---|
| 发布指挥 | 决策放量/暂停/回滚，统一对外口径 | 发布日全程 |
| 技术值班 | 监控系统/支付/AI 成本，处理线上问题 | 发布日全程 + 首周高峰时段 |
| 运营/客服值班 | 处理用户反馈、内容审核、举报 | UAE 时区活跃时段 |

> 小团队可一人多岗，但**发布指挥与回滚决策权须明确到人**。

### 5.2 事故分级与响应

| 级别 | 定义 | 示例 | 响应 |
|---|---|---|---|
| **P0** | 核心不可用/资金或合规风险 | 支付错账、鉴权失效、数据泄露、合规违规 | 立即暂停放量，必要时回滚；第一时间处置 |
| **P1** | 关键功能受损但有临时规避 | 通知不达、匹配异常、AI 调用大面积失败 | 当日修复或降级，暂缓放量 |
| **P2** | 体验问题，不阻塞核心 | 文案/样式/非关键页报错 | 排期修复，不影响放量 |

### 5.3 应急预案要点

- **支付异常**：暂停下单入口、核对回调与对账、幂等补偿；必要时人工介入退款。
- **AI 成本超预算**：触发预算保护，降级到更低配额/更小模型或临时限流 AI 功能。
- **内容安全事件**：加严审核阈值、暂停问题用户、走举报复核闭环。
- **性能问题**：限流、扩容或暂缓放量。

## 6. 发布后观察指标与回滚触发条件

### 6.1 发布后核心观察指标（首周重点）

| 维度 | 指标 | 健康信号 |
|---|---|---|
| 稳定性 | 崩溃率 / 5xx 错误率 / 接口 P95 延迟 | 低且平稳 |
| 支付 | 支付成功率 / 回调成功率 / 对账一致 | 高且账目一致 |
| 激活 | 注册完成率 / 首日建立首个匹配比例 | 达到预期 |
| 留存 | 次日留存 | 达到或高于预期基线 |
| 供需密度 | 匹配成功率 / 消息回复率 | 稳定、无骤降 |
| AI 成本 | 月度预算使用率 / 单用户 token 消耗 | 在 $500/月 预算内可控 |
| 安全 | 举报量 / 内容审核命中 / 异常登录 | 无异常激增 |

### 6.2 回滚 / 暂停放量触发条件

出现以下任一情况，**立即暂停放量并评估回滚**：

- **支付**：支付成功率骤降、出现错账/重复扣款/对账不一致（P0）。
- **安全/合规**：数据泄露、鉴权失效、PDPL 合规风险或监管问询（P0）。
- **稳定性**：5xx 错误率或崩溃率突破阈值、核心接口大面积超时（P0/P1）。
- **AI 成本**：月度预算使用率异常飙升逼近/超出 $500 且无法快速降级（P1）。
- **内容安全**：违规内容/骚扰举报激增，审核无法及时闭环（P1）。

> **回滚原则**：优先"暂停放量 + 热修复/降级"，仅在无法快速止血时执行版本回滚；回滚须确认数据回滚点，避免支付/订阅数据不一致。
