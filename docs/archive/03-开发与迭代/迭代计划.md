# 03 · 迭代计划

> UAE Match ｜ 版本 v1.0.0 ｜ 更新 2026-07-04

---

## 1. 迭代方法

UAE Match 采用 **Scrum 精简版**（适配单人 / 小团队），以 **2 周为一个 Sprint** 的固定节奏推进。核心原则：

- **迭代交付**：每个 Sprint 结束都有可演示、可验证的增量，而非等到全部完成才交付。
- **对齐路线图**：Sprint 1–4 全部服务于**第一阶段 · 商业化闭环（对应里程碑 M1）**——把产品从"能演示"推进到"能收钱、能触达"。
- **P0 优先**：小团队人力有限，严格按优先级排布 Backlog，先做阻塞商业化的关键路径（支付 → 会员权益授权）。
- **务实**：紧扣真实代码现状（支付框架已在、通知为桩、前端有演示态），改造以"补齐"为主而非重写。

> 一个 Sprint = 2 周（10 个工作日）。4 个 Sprint ≈ 8 周，覆盖 M1 商业化闭环（计划第 1–6 周，预留 2 周缓冲）。

---

## 2. Sprint 节奏与仪式（单人 / 小团队版）

标准 Scrum 仪式在小团队下可简化，但**保留其价值**（对齐目标、暴露阻塞、沉淀改进）。

| 仪式 | 时机 | 时长 | 小团队做法 |
|---|---|---|---|
| **Sprint 计划** | Sprint 第 1 天上午 | 1–2 小时 | 从 Backlog 选定本 Sprint 目标与故事，拆任务、估工作量、明确 DoD |
| **每日站会** | 每个工作日 | 5–10 分钟 | 单人可用"每日三问"自检并记录：昨天做了什么 / 今天做什么 / 有无阻塞；多人则同步对齐 |
| **Sprint 评审（Demo）** | Sprint 最后一天上午 | 30–60 分钟 | 演示本 Sprint 可运行成果，对照 DoD 验收，未完成项回流 Backlog |
| **Sprint 回顾** | Sprint 最后一天下午 | 30 分钟 | 复盘：做得好 / 待改进 / 下 Sprint 的 1–2 个改进行动 |
| **Backlog 梳理** | Sprint 中期（第 5–6 天）随手 | 30 分钟 | 澄清下个 Sprint 候选故事，补充验收标准 |

**看板列建议**：`待办(Backlog)` → `本 Sprint(Todo)` → `进行中(Doing)` → `待验收(Review)` → `完成(Done)`。单人建议限制"进行中"最多 2 张卡（限制在制品，减少上下文切换）。

---

## 3. Sprint 规划总览

| Sprint | 周次 | Sprint 目标（一句话） | 对应缺口 |
|---|---|---|---|
| **Sprint 1** | 第 1–2 周 | 打通一条真实支付链路的下单→回调→订单落库 | 支付未接真实网关 |
| **Sprint 2** | 第 3–4 周 | 支付闭环收尾 + 会员权益由服务端订阅状态授权 | 支付闭环、VIP 前端开关 |
| **Sprint 3** | 第 5–6 周 | 通知系统从桩实现补全，关键事件可触达 | 通知桩实现 |
| **Sprint 4** | 第 7–8 周 | 前端去演示态（照片/编辑资料）+ 安全加固基线 | 前端演示态、JWT/Key 安全 |

> 说明：安全加固（JWT 密钥治理、OpenAI Key 轮换）虽属 M3 范畴，但因风险高、改动小，提前在 Sprint 4 做基线加固，避免演示态改造后带着弱密钥进入灰度。

## 4. 各 Sprint 详情

### Sprint 1 · 支付网关真实对接（第 1–2 周）

**Sprint 目标**：至少一条真实支付链路（建议先做面向华人用户的支付宝或微信）跑通"下单 → 跳转支付 → 回调验签 → 订单/订阅落库"。

| 优先级 | 用户故事 | 验收要点 |
|---|---|---|
| P0 | 作为用户，我能对某个会员计划发起真实下单并跳转到支付渠道 | `/payment` 创建订单返回真实支付参数/跳转链接 |
| P0 | 作为系统，我能接收支付回调并**验签**，幂等地更新订单状态 | 回调验签通过；重复回调不重复入账（幂等） |
| P0 | 作为系统，支付成功后订单 → 订阅记录正确落库 | `subscriptions` 生成，起止时间、计划类型正确 |
| P1 | 作为运营，我能在后台看到订单与支付状态 | 后台订单列表展示真实支付状态 |
| P1 | 支付失败/超时有明确处理与用户提示 | 失败订单标记清晰，前端有反馈 |

**技术前置**：支付渠道商务/资质申请须**在本 Sprint 之前或期间并行启动**（外部审批不可控）；沙箱环境优先。

**Demo 成果**：在沙箱环境完成一次真实下单并回调成功，订单与订阅在数据库中正确落库。

---

### Sprint 2 · 支付闭环收尾 + 会员权益服务端授权（第 3–4 周）

**Sprint 目标**：支付链路达到可用（含续费与增值服务下单），并**将 VIP 判定从前端开关迁移为服务端订阅状态授权**——这是从"能演示 VIP"到"真实卖 VIP"的关键跨越。

| 优先级 | 用户故事 | 验收要点 |
|---|---|---|
| P0 | 作为付费用户，我的 VIP/会员权益由服务端订阅状态决定 | 移除前端 VIP 硬编码开关；权益判定读订阅状态 |
| P0 | 作为 basic/premium 会员，我的额度与特权按计划真实生效 | 匹配额度、超级喜欢、已读、高级特权按订阅差异化 |
| P0 | 作为用户，我能购买增值服务（超级喜欢/Boost/查看谁喜欢我） | 增值商品下单→支付→权益即时到账 |
| P1 | 作为用户，我的订阅到期能自动续费或到期降级 | `auto_renew` / `next_billing_date` 真实生效 |
| P1 | 作为用户，前端会员中心展示我的订阅状态与额度 | 会员中心显示当前计划、到期日、剩余额度 |

**Demo 成果**：用测试账号购买 premium 后，服务端授权其高级特权；到期或退订后权益回落；一次增值服务购买即时生效。

---

### Sprint 3 · 通知系统落地（第 5–6 周）

**Sprint 目标**：将通知从**桩实现（返回空）**补全为真实的存储 + 站内通知，覆盖核心触发事件；Web Push 作为可选延伸。

| 优先级 | 用户故事 | 验收要点 |
|---|---|---|
| P0 | 作为系统，关键事件能产生并持久化通知 | 新匹配 / 新消息 / 被喜欢 / 订阅到期 落库为通知记录 |
| P0 | 作为用户，我能在站内看到未读通知并标记已读 | 通知列表 + 未读数 + 已读状态可用 |
| P1 | 作为用户，我能接收 Web Push 浏览器推送 | 订阅推送权限，关键事件触发浏览器通知 |
| P1 | 作为用户，我能配置接收哪些类型通知（防打扰） | 通知偏好设置生效 |
| P2 | 作为系统，通知与现有 VIP 主动关怀机制不冲突 | 关怀消息与通知去重、频控 |

**Demo 成果**：A 喜欢 B、两人互相喜欢、发送消息后，B 站内实时收到对应通知并可标记已读；订阅到期产生提醒通知。

---

### Sprint 4 · 前端去演示态 + 安全加固基线（第 7–8 周）

**Sprint 目标**：清除阻碍真实运营的前端演示态（照片、编辑资料），并完成上线前的安全基线（密钥治理），为灰度做准备。

| 优先级 | 用户故事 | 验收要点 |
|---|---|---|
| P0 | 作为用户，我的照片走真实上传/审核/展示流程 | 去除"注册后 10 秒自动过审"演示逻辑，审核状态真实 |
| P0 | 作为用户，我能真实编辑并保存我的资料 | 前端调用 `PUT /profile/me`，去除 mock 兜底 |
| P0 | 作为系统，JWT 双密钥为强随机且走环境变量 | 无默认/明文密钥；密钥从环境变量注入 |
| P0 | 作为系统，OpenAI Key 完成轮换且不入代码库 | Key 走环境变量/密钥管理，历史泄露 Key 作废 |
| P1 | 作为运营，我能通过后台真实处理照片审核 | 后台审核队列可通过/驳回，状态回写 |

**Demo 成果**：新用户注册后照片进入真实审核态、由后台人工过审后展示；编辑资料真实保存；服务以环境变量注入的强随机密钥启动，代码库无明文密钥。

## 5. 完成定义（Definition of Done, DoD）

一个用户故事/任务被视为"完成"，需**同时满足**以下条件：

| 类别 | 完成标准 |
|---|---|
| 功能 | 满足该故事的全部验收要点；前后端联调通过，非 mock、非演示态 |
| 代码 | 已合入主干（或经评审的分支）；关键逻辑有注释；无遗留 TODO 阻塞项 |
| 测试 | 关键路径有基本测试或手动测试记录；边界与失败场景已验证（尤其支付幂等、验签） |
| 安全 | 不引入默认/明文密钥；涉及支付/鉴权的改动经安全自检 |
| 数据 | 涉及表结构变更有迁移方案（M3 前用脚本，M3 起用 Alembic） |
| 文档 | 相关文档同步更新（含本迭代计划、CHANGELOG 的 Unreleased 条目） |
| 可演示 | 能在 Sprint 评审上以真实运行方式演示，通过 DoD 验收 |

> **Sprint 完成定义**：本 Sprint 目标达成、承诺的 P0 故事全部 Done、Demo 通过验收、回顾产出下一 Sprint 改进项；未完成故事明确回流 Backlog 并重排优先级。
