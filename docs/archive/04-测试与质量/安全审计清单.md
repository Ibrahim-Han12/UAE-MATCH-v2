# 04 · 安全审计清单

> UAE Match ｜ 版本 v1.0.0 ｜ 更新 2026-07-04

本清单用于对 UAE Match（FastAPI + SQLite + OpenAI 后端，React + Vite 前端）进行安全审计，逐项给出**检查点**与**建议**，并针对 v1.0 已知安全缺口设专项检查。婚恋平台涉及大量个人敏感信息与真实社交关系，安全等级要求高。

**结论标记**：🟢 通过 / 🟡 有风险需改进 / 🔴 高危需上线前处置 / ⚪ 待验证。

---

## 1. 通用安全检查清单

### 1.1 认证与授权

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 认证机制 | 所有受保护接口是否强制 `Authorization: Bearer`；`/auth/me` 等无 token 返回 401 | 统一依赖注入校验；缺 token/过期/篡改均 401 | 🟢 |
| 令牌有效期 | access 30 分钟、refresh 7 天是否生效；过期后拒绝 | 保持短 access + refresh 续期；考虑 refresh 轮换 | 🟢 |
| 越权（水平） | 用户 A 能否读/改用户 B 的资料、照片、会话、订单 | 所有资源操作校验归属（`/me` 语义 + owner 校验） | ⚪ 重点验证（TC-PROF-09/PHOTO-11/CHAT-12/SAFE-08） |
| 越权（垂直） | 普通用户能否访问 `/admin/*` | 校验 `is_admin`，非管理员一律 403 | ⚪ 验证 TC-ADMIN-06 |
| 前端权益判定 | VIP 权益是否仅靠前端 `isVIP` 开关 | 真实权益必须后端 `/subscription/status` 判定；前端开关仅演示 | 🟡 |

### 1.2 JWT 与密钥

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| JWT 签名密钥 | `JWT_SECRET_KEY`/`JWT_REFRESH_SECRET_KEY` 是否仍为默认值 | 上线前改为高强度随机值，走环境变量/密钥管理；见专项 §2.1 | 🔴 |
| 算法 | 是否固定 HS256、拒绝 alg=none | 显式指定算法白名单，禁止 none | ⚪ |
| access/refresh 密钥分离 | 两类令牌是否用不同密钥 | 保持分离（当前设计已分离） | 🟢 |

### 1.3 密码安全

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 哈希算法 | 是否 PBKDF2-SHA256（passlib），无明文存储 | 保持；确认迭代次数足够 | 🟢 |
| 密码策略 | 是否有最小长度/复杂度校验 | 增加最小长度与弱口令拦截 | 🟡 |
| 传输 | 登录/注册是否走 HTTPS | 生产强制 HTTPS，见 §1.11 | ⚪ |

### 1.4 输入校验

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 参数校验 | 邮箱格式、gender 枚举、min_age≤max_age、举报 category 枚举 | Pydantic schema 严格校验，返回 422 | ⚪ 验证 TC-PROF-07/08、SAFE-07 |
| SQL 注入 | 是否全部经 SQLAlchemy 参数化 | 禁止字符串拼 SQL；保持 ORM 参数化 | 🟢 |
| XSS | 用户内容（bio/消息/昵称）在前端是否转义渲染 | React 默认转义；避免 dangerouslySetInnerHTML | ⚪ |
| 消息长度 | ≤1000 字是否强制 | 服务端强校验（TC-CHAT-07） | ⚪ |

### 1.5 内容审核

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 审核覆盖 | 聊天/资料是否经 `detect_content_risk`；BLOCKED/HIGH 是否拦截 | 拦截生效（TC-CHAT-09/10）；见专项 §2.3 | 🟡 |
| 绕过风险 | 谐音/拼音/图片/变形词能否绕过关键词 | 升级 AI 审核 + 图片审核 + 人工复核 | 🟡 |

### 1.6 限流与防刷

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 消息限流 | 10 秒 ≤20 条是否生效（429） | 保持滑动窗口（TC-CHAT-08） | ⚪ |
| 分析限流 | match-insights 30 次/分是否生效 | 保持（TC-INSIGHT-05） | ⚪ |
| 登录防爆破 | 登录是否有失败次数限制 | 增加登录限流/锁定，防撞库 | 🔴 缺失，建议补 |
| AI 配额/预算 | token/推荐/全局预算超限是否 403 且不调 OpenAI | 保持（TC-QUOTA-*） | 🟢 |

### 1.7 文件上传安全

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 类型/大小 | 是否仅允许 JPEG/PNG/WebP、≤10MB、≤9 张 | 服务端强校验（TC-PHOTO-08/09/10） | ⚪ |
| 真实类型 | 是否按真实 MIME/魔数校验，防伪装扩展名 | 校验文件头，非仅扩展名（TC-PHOTO-12） | 🟡 |
| 存储路径 | 是否防目录穿越；文件名是否随机化 | 随机文件名、隔离目录、禁止执行权限 | ⚪ |
| 下载接口 | `/photos/file/{filename}` 无鉴权是否有信息泄露风险 | 用随机不可枚举文件名；敏感场景加签名 URL | 🟡 |

### 1.8 敏感数据加密与隐私

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 静态数据 | SQLite 文件是否加密/受控访问 | 迁 PostgreSQL 后启用磁盘/字段加密 | 🟡 |
| 传输加密 | 是否全站 HTTPS/WSS | 强制 TLS（含 WebSocket） | ⚪ |
| PII 最小化 | 日志是否记录密码/token/联系方式 | 日志脱敏，禁记凭证 | ⚪ |
| 合规 | 数据导出/注销、跨境（UAE↔中国）合规 | 提供账号注销与数据导出，做合规审查 | 🟡 |

### 1.9 密钥管理

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| Key 存储 | OpenAI Key、JWT 密钥、DB 凭证是否在环境变量/密钥服务，不入库不入前端 | 用 Secret Manager；`.env` 不入版本库 | 🟡 |
| Key 历史泄露 | OpenAI Key 曾明文于 `.env` | 立即轮换，见专项 §2.2 | 🔴 |

### 1.10 CORS

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 来源白名单 | 是否限制到前端域名，非 `*` | 生产用精确白名单，禁止通配 + 凭证同时开启 | ⚪ |

### 1.11 HTTPS / 传输

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 强制 HTTPS | 是否全站重定向 HTTPS，启用 HSTS | 启用 TLS + HSTS；WebSocket 用 WSS | ⚪ |
| 安全响应头 | CSP、X-Content-Type-Options、X-Frame-Options | 增加安全响应头 | 🟡 |

### 1.12 依赖漏洞

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 后端依赖 | FastAPI/SQLAlchemy/passlib 等是否有已知 CVE | `pip-audit` 定期扫描并升级 | ⚪ |
| 前端依赖 | React/Vite 及 npm 包 | `npm audit` 定期扫描 | ⚪ |

### 1.13 日志与审计

| 项 | 检查点 | 建议 | 初判 |
|---|---|---|---|
| 审计事件 | 登录、举报、拉黑、风险事件是否入 `event_logs` | 保持并补关键操作审计 | 🟢 |
| 管理操作留痕 | 管理员处理举报/关联事件是否可追溯 | 记录操作人与时间 | ⚪ |
| 日志安全 | 日志访问是否受控、是否脱敏 | 访问控制 + 脱敏 | 🟡 |

## 2. 本项目已知安全缺口专项检查

### 2.1 JWT 默认密钥 🔴

- **问题**：`JWT_SECRET_KEY` / `JWT_REFRESH_SECRET_KEY` 使用默认值。攻击者可用公开默认值自签任意 `sub`(user_id) 的令牌，伪造任意用户身份、冒充管理员。
- **检查点**：确认生产环境密钥为高强度随机值且非默认；尝试用默认密钥自签令牌访问受保护接口应失败（TC-AUTH-11）。
- **建议**：上线前通过环境变量注入随机密钥（≥32 字节）；纳入部署检查清单，作为发布阻塞项；后续考虑密钥轮换机制。

### 2.2 OpenAI Key 轮换 🔴

- **问题**：OpenAI Key 曾明文出现在 `.env`，存在历史泄露风险。
- **检查点**：确认旧 Key 已废弃/轮换；`.env` 未进版本库；前端与日志不含 Key；AI 调用仅经后端代理。
- **建议**：立即轮换新 Key，旧 Key 吊销；用密钥管理服务托管；设置用量告警监控异常消耗（防被盗刷）。

### 2.3 内容审核仅关键词/正则 🟡

- **问题**：`detect_content_risk` 仅基于约 150 词分类关键词 + 正则高危模式，无语义理解，易被谐音/拼音/变体/图片绕过，也可能误伤正常内容。
- **检查点**：用变形词、图片、拼音测试拦截率；统计误判/漏判样本。
- **建议**：升级为 LLM/第三方审核 API + 图片审核，保留关键词作为快速前置；高风险内容进人工复核队列；结合举报与风控事件联动。

### 2.4 SQLite 存储 🟡

- **问题**：SQLite 单文件、并发弱、无内建加密与细粒度访问控制；向量以 JSON 存于 `user_embeddings`，检索为 O(n) 线性扫描。
- **检查点**：确认 DB 文件权限受限、不可公开访问；评估并发下锁竞争与数据完整性。
- **建议**：按路线图迁移 PostgreSQL + pgvector + HNSW；启用连接加密与备份；引入 Alembic 管理迁移，避免手写脚本导致结构漂移。

### 2.5 支付回调未验签（关联缺口）🔴

- **问题**：`POST /payment/callback` 无需鉴权且未接真实网关，若无来源校验/验签，可被伪造回调开通会员或篡改订单。
- **检查点**：伪造回调请求（TC-PAY-06）应被拒绝；重复回调需幂等（TC-PAY-07）。
- **建议**：对接真实网关时实现签名验证、来源 IP 白名单、金额与订单一致性校验、幂等处理。

## 3. 威胁清单（Threat List）

| 威胁 | 场景 | 主要缓解措施 |
|---|---|---|
| 账号盗用 | 撞库/爆破/令牌伪造（默认密钥）冒充登录 | 登录限流+锁定、强密码策略、随机 JWT 密钥、HTTPS、可疑登录告警 |
| 垃圾与诈骗信息 | 聊天群发诈骗、引流联系方式 | 内容审核（升级 AI）、消息限流（10s≤20）、举报+拉黑、风控事件联动 |
| 虚假资料 | AI 生成/盗图/夸大信息骗取信任 | 照片/实名/学历认证徽章、真实类型校验、人工抽审、举报处理 |
| 数据泄露 | PII/聊天记录/向量被越权访问或库泄露 | 越权防护、静态/传输加密、日志脱敏、DB 访问控制、Key 托管 |
| AI 滥用刷量 | 恶意大量调用 AI 接口刷高成本/耗尽预算 | token 配额（10000/月）、推荐额度（2/月）、全局预算（500 USD）超限 403、限流、异常用量告警 |
| 支付欺诈 | 伪造/重放回调、篡改金额 | 回调验签、幂等、金额校验、来源白名单 |
| 骚扰与安全风险 | 线下见面安全、持续骚扰 | 拉黑/举报、安全提示（safety_tips 4条）、管理后台处置、事件审计 |

## 4. 审计执行与跟踪

- 每次发布前执行本清单；🔴 项为上线阻塞项，必须关闭或有明确风险接受记录。
- ⚪ 项在测试执行后更新为 🟢/🟡/🔴 并记录证据（请求/响应/截图/日志）。
- 高危缺口（§2.1、§2.2、§2.5、登录防爆破缺失）纳入《测试计划.md》缺陷跟踪，按 P0/P1 处理。
