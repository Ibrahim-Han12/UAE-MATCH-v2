# 04 · 测试计划

> UAE Match ｜ 版本 v1.0.0 ｜ 更新 2026-07-04

本文档定义 UAE Match（面向阿联酋华人的 AI 相亲平台）v1.0.0 的测试策略、范围、组织与准则。测试目标紧扣真实实现：FastAPI + SQLAlchemy + SQLite（拟迁 PostgreSQL）后端、约 58 个 `/api/v1` 接口、20 张数据表、9 类核心算法，以及 React 18 + Vite 前端。

---

## 1. 测试目标

| 目标 | 描述 |
|---|---|
| 功能正确性 | 58 个接口在正常/边界/异常输入下行为符合 LLD 定义（如 `POST /api/v1/matches/action` 正确返回 `is_mutual_match`）。 |
| 差异化能力保障 | 核心壁垒——AI 向量语义匹配（余弦相似度 ≥0.7 取 Top5）、AI 红娘小缘、实时聊天（WebSocket）——功能与稳定性达标。 |
| 成本与配额可控 | token 配额（默认 10000/月）、推荐额度（默认 2/月）、全局预算（默认 500 USD/月）在超限时正确返回 403。 |
| 安全与合规 | 认证授权、内容审核、限流防刷、越权防护有效；识别并记录 v1.0 已知安全缺口。 |
| 上线风险可见 | 明确标注演示态（10 秒自动过审、VIP 前端开关、mock 兜底）与桩实现（通知、支付网关）对测试结论的影响。 |

## 2. 测试范围

### 2.1 范围内（In Scope）

| 模块 | 关键接口/能力 |
|---|---|
| 账户与认证 | `/auth/register`、`/auth/login`、`/auth/refresh`、`/auth/me` |
| 资料与偏好 | `/profile/me`、`/preferences/me` |
| 照片系统 | `/photos/upload`（≤9张/≤10MB/JPEG·PNG·WebP）、`/photos/reorder`、`/photos/{id}` |
| AI 引导注册 | `/ai-chat/start-registration`、`/send-message`、`/complete-registration` |
| 智能匹配 | `/matches/suggestions`（rule/ai）、`/matches/action`、`/matches/my-matches`、`/matches/who-liked-me`、`/match/recommend` |
| AI 匹配分析 | `/coach/match-insights`（缓存30天、20条/人、限流30次/分） |
| 实时聊天 | `/chats/*`（REST）、`WS /ws/chat/{id}`（发消息≤1000字、10秒≤20条、内容审核、已读） |
| AI 红娘咨询 | `/ai-chat/send-message`（consultation）、`/token-usage`、`/recommendation-quota`、`/memory-summary`（VIP） |
| 安全风控 | `/safety/block`、`/safety/report`、内容审核、限流、事件日志 |
| 支付订阅 | `/payment/create-order`、`/payment/callback`、`/subscription/status`、`/products`（框架层面） |
| 管理后台 | `/admin/reports`、`/admin/events`、`/admin/stats`、`/admin/reports/{id}/link-events` |
| 数据分析 | `/analytics/me/snapshot`、`/analytics/me/match-context` |
| 前端 | 状态机导航、认证会话、5 个主页面、悬浮 AI 气泡、字段转换（男女↔male/female、age↔birth_year） |

### 2.2 范围外 / 受限测试（Out of / Limited Scope）

| 项 | 原因 | 测试策略 |
|---|---|---|
| 支付真实收款 | 未接真实网关（支付宝/微信/信用卡） | 仅测下单/回调/订阅状态的框架逻辑，用模拟回调；不做真实资金链路。 |
| 通知触达 | `/notifications/*` 为桩，返回空/0 | 仅验证接口可访问、返回结构；不测实际推送。 |
| VIP 真实权益 | 前端 `isVIP` 为前端开关，非真实订阅态 | 前端权益展示按开关测；真实权益判定以 `/payment/subscription/status` 为准分开验证。 |
| 待审核自动过审 | 演示态 10 秒自动通过 | 标注为演示行为，不作为真实审核流程的通过判据。 |
| 多语言 | 仅中文 | 不测英/阿语。 |
| 移动 App | 未开始 | 不在范围。 |

## 3. 测试类型

| 类型 | 重点 | 工具/方式 |
|---|---|---|
| 单元测试 | 核心算法函数：`cosine_similarity`、`build_profile_text`、`detect_content_risk`、`check_rate_limit`、密码哈希（PBKDF2-SHA256）、JWT 生成/校验、滚动摘要 token 估算 | pytest |
| 集成测试 | 服务间链路：`/match/recommend`（配额+预算→SQL硬过滤→向量排序→GPT 理由→计费）、AI 引导注册→抽取落库→建向量 | pytest + 测试 DB + OpenAI mock |
| 接口测试 | 58 个 REST 接口的状态码、鉴权、请求/响应契约、错误码（401/403/404/422/429） | pytest + httpx / Postman |
| 端到端（E2E） | 关键旅程：注册引导→推荐→喜欢→互相匹配→聊天；AI 咨询 | 前端手工 + 可选 Playwright |
| 安全测试 | 认证授权、越权、JWT 默认密钥、输入校验、限流防刷、文件上传、内容审核绕过 | 详见《安全审计清单.md》 |
| 性能测试 | 向量检索 O(n) 线性扫描随用户量的表现、聊天并发、AI 接口响应时延、限流边界 | locust / k6 |
| 兼容性测试 | 移动优先 Web（iOS Safari / Android Chrome / 桌面 Chrome/Edge），localStorage 令牌行为 | 多端手工 |
| 用户验收（UAT） | 目标用户（UAE 华人）真实旅程体验、AI 匹配主观满意度、AI 红娘对话质量 | 邀请测试用户 |

## 4. 测试环境

| 环境 | 用途 | 配置要点 |
|---|---|---|
| 本地（Local） | 开发自测、单元/集成 | SQLite；OpenAI 可用 mock 桩或真实 Key（低配额）；`JWT_SECRET_KEY` 使用测试值。 |
| 预发（Staging） | 接口/E2E/性能/安全 | 尽量对齐生产（拟迁 PostgreSQL 后在此验证向量与迁移）；独立 OpenAI Key 与预算；模拟支付回调环境。 |
| 生产（Prod） | 冒烟验证 | 仅 `/health` 及只读冒烟；不做破坏性测试。 |

环境差异对测试的影响需在报告中标注：SQLite（本地）与 PostgreSQL（生产目标）在并发、向量检索性能、唯一约束行为上可能不同，向量相关性能测试应在预发 PG 环境复测。

## 5. 进入与退出准则

### 5.1 进入准则（Entry）

- 被测版本已部署到目标环境且 `GET /api/v1/health` 返回 `{"status":"ok"}`。
- 测试数据（见第 7 节）准备就绪。
- 冒烟用例（注册→登录→取资料→取推荐）全部通过。
- 相关接口文档（LLD）与需求（BRD/PRD）已冻结基线。

### 5.2 退出准则（Exit）

| 条件 | 标准 |
|---|---|
| 用例执行率 | ≥ 98% |
| 用例通过率 | 核心模块（认证/匹配/聊天/AI/安全）≥ 98%；整体 ≥ 95% |
| 缺陷收敛 | P0/P1 缺陷全部关闭；P2 关闭率 ≥ 90%，剩余有明确计划 |
| 需求覆盖 | RTM（需求追溯矩阵）覆盖率 100%，核心需求均有对应用例 |
| 安全 | 《安全审计清单》高危项全部有结论；已知缺口（JWT 默认密钥等）已记录并有上线前处置计划 |

## 6. 缺陷分级与处理流程

### 6.1 缺陷分级（P0–P3）

| 级别 | 定义 | 示例（本项目） | 期望处理时限 |
|---|---|---|---|
| P0（致命） | 核心链路不可用、安全事故、数据损坏 | 登录失败无法进入；`/match/recommend` 500；JWT 默认密钥导致令牌可伪造；越权读取他人资料 | 立即修复，阻塞发布 |
| P1（严重） | 主要功能缺陷、无合理绕过 | 互相匹配未建立 `match_pairs`；WebSocket 消息丢失；内容审核对 BLOCKED 词未拦截；配额超限未返回 403 | 当日修复 |
| P2（一般） | 次要功能缺陷、有绕过 | 照片重排后主图未自动设置；`match-insights` 缓存未命中重复计费；分页 skip/limit 边界异常 | 版本内修复 |
| P3（轻微） | 体验/文案/非阻塞 | 错误提示文案不准确；时间戳时区显示；空态样式 | 计划修复 |

### 6.2 处理流程

```
发现缺陷 → 提单(标题/环境/步骤/期望vs实际/日志/截图/接口与请求体)
   → 定级(P0–P3) → 指派开发 → 修复 → 提测
   → 回归验证 → 通过则关闭 / 未通过则打回重开
   → P0/P1 需在缺陷评审会同步
```

- 演示态/桩实现引发的"预期不达真实业务"应标注为 **已知限制（Known Limitation）**，与真实缺陷分开统计，避免误判发布风险。

## 7. 测试数据准备

| 数据类别 | 准备内容 |
|---|---|
| 用户账户 | 男/女各若干；含仅邮箱、仅手机、邮箱+手机三类；含 `is_admin=true` 管理员账户 |
| 资料与偏好 | 完整资料 vs 缺失 `bio`；覆盖 UAE 城市、在 UAE 时长、定居/回国、结婚时间线、子女意愿等本地化维度；偏好覆盖年龄/身高/收入/学历/宗教/MBTI |
| 向量 | 已建 `user_embeddings` 的用户 vs 未建向量用户（验证匹配可用性与兜底） |
| 匹配关系 | 单向 like、双向 like（应建 `match_pairs`）、已拉黑、已举报 |
| 聊天 | 已有会话与历史消息；含未读消息；含命中审核词（SAFE/LOW/MEDIUM/HIGH/BLOCKED 各级样本） |
| 配额与预算 | 接近上限、已达上限的 `user_token_usage`/`user_recommendation_quota`/`global_ai_budget` 记录 |
| 订阅 | free / basic / premium 三类订阅态；含过期订阅 |
| 照片 | 合规图（JPEG/PNG/WebP，<10MB）；超大图（>10MB）；错误类型（GIF/PDF）；已上传 9 张的账户 |
| OpenAI | mock 桩（离线可测）与真实 Key（限额，用于成本相关验证） |

数据准备原则：预发环境使用脱敏/合成数据；不使用真实用户隐私数据；测试后清理。

## 9. 测试风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| OpenAI 依赖不稳定/限额 | AI 匹配、红娘、分析等用例无法执行或结果不确定 | 优先用 mock 桩测逻辑；真实调用用独立限额 Key；断言结构而非具体文本 |
| AI 输出不确定性 | 推荐理由/分析文本难以精确断言 | 断言字段存在与格式（如 `match_score_breakdown` 4 维 0–1、opener 条数），不断言具体措辞 |
| SQLite 与 PostgreSQL 差异 | 本地测试通过但生产表现不同（并发、向量性能） | 关键性能/并发用例在预发 PG 复测 |
| 演示态干扰判断 | 10 秒过审、VIP 前端开关、mock 兜底被误当真实功能 | 严格区分演示态与真实态，单独标注 |
| 支付/通知为桩 | 无法端到端验证收款与触达 | 限定为框架测试，发布结论中明示未覆盖真实链路 |
| 已知安全缺口 | JWT 默认密钥、内容审核仅关键词、Key 明文历史 | 纳入安全审计清单专项，列为上线前阻塞项 |
| 成本失控 | 测试期间大量 AI 调用超预算 | 测试账户使用低配额；监控 `global_ai_budget`；批量场景用 mock |
